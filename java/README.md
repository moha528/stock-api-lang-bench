# Stock API — Java

- **Pile** : JDK 25 (LTS) + **Vert.x 5.2.2** (`vertx-core` seul, sans vertx-web) + **`vertx-pg-client`** réactif. C'est la pile Java en tête des TechEmpower : boucle d'événements Netty non bloquante, pas de thread par requête, ce qui convient à une machine de 1 vCPU / 512 Mo. Pas de Spring.
- **Postgres** : client « pipeliné » (`PgBuilder.client()`), `DB_POOL_MAX` connexions, jusqu'à 256 requêtes en vol par connexion, requêtes préparées mises en cache par connexion. Le SQL est celui de `SPEC.md`, mot pour mot.
- **HTTP** : routage à la main sur `path()` et la méthode, réponses d'erreur pré-encodées, `Content-Type` en en-tête optimisé, transport natif **epoll**, h2c désactivé. Une boucle d'événements par vCPU.
- **JVM** (`jvm.options` + `entrypoint.sh`) : le GC dépend du quota CPU du conteneur. À 1 CPU c'est **SerialGC** : il n'y a pas de cœur libre pour un GC concurrent, et Serial a les barrières les moins coûteuses. Au-delà c'est **ParallelGC** : les collections jeunes sont parallèles sur tous les cœurs avec la même barrière légère, alors que les barrières de G1 coûtent cher sur du code qui déplace des références (tri, tableaux de String). `-XX:NewRatio=1` donne une génération jeune de la moitié du tas, ce qui limite la promotion des données encore en vol des traitements lourds. Le tas est fixé à 70 % de la RAM (Initial = Max, ~358 Mo), il reste ~150 Mo pour la métaspace, le code JIT et les buffers directs de Netty. `-XX:+UseCompactObjectHeaders` (JEP 519) donne des en-têtes de 8 octets, donc moins de mémoire et de GC. `ExitOnOutOfMemoryError`, et les vérifications de bornes des buffers Netty sont désactivées.
- **Démarrage** : **cache AOT** du JDK 25 (JEP 483/514/515). Le build en produit un par GC (`serial.aot`, `parallel.aot`) avec une exécution d'entraînement qui couvre aussi `/cpu/*`. Le JIT C2 reste actif, pas de native-image.
- **Traitements lourds** (`Heavy.java`, SPEC-heavy.md) : le calcul ne passe jamais sur la boucle d'événements. Il part sur un `WorkerExecutor` Vert.x de taille fixe égale à `availableProcessors()` (file non bornée), avec `executeBlocking(…, false)`, et la réponse revient sur le contexte de la requête.
- **hash** : `MessageDigest` SHA-256, intrinsèque HotSpot (SHA-NI), avec `digest(h, 0, 32)` sans allocation par tour. **montecarlo** : la boucle double suit l'ordre exact de la spec, sans FMA (C2 n'en génère pas de lui-même) et avec une somme séquentielle. splitmix64 est en `long` local, avec `>>>` et `Long.remainderUnsigned`.
- **reconcile** : les références sont des `String` Latin-1 construites depuis un tampon réutilisé. La table String→int est à adressage ouvert et pré-dimensionnée, sans `Integer` ni nœud par entrée. **sort** : `Arrays.sort` (TimSort séquentiel) sur des `String` Latin-1, dont le `compareTo` intrinsèque suit l'ordre des octets.
- **commissions** : le corps (16 Mo au plus, une limite que vertx-core n'impose pas) est accumulé dans un tableau dimensionné par `Content-Length`. Il est lu par Jackson en streaming (`jackson-core` 2.21.7, déjà apporté par Vert.x), et chaque agent est retrouvé sur les caractères du parseur, donc une seule `String` par agent et aucune par ligne. Les lignes sont rangées dans des tableaux primitifs. Partout, le JSON de sortie est écrit directement dans un `byte[]` enveloppé sans copie dans le `Buffer` de la réponse.
- **Image** : build multi-étapes Maven, avec le dépôt `.m2` en cache BuildKit. Le JRE est produit par `jlink` (modules choisis par `jdeps`) sur `alpine:3.22`, tourne sous un utilisateur non root, et `java` est le PID 1 : SIGTERM déclenche l'arrêt gracieux du serveur HTTP, puis du pool.
